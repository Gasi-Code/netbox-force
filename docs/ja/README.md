## 1. このプラグインの役割

NetBox は *何が* 変わったかを記録します。NetBox Force は *そもそもその変更を認めて
よいか* を判断し、通す前に理由を求めることができます。

すべての保存・削除操作とデータベースの間に位置します。変更が書き込まれる前に、次を
確認できます。

- 変更ログのコメントが入力され、十分な長さがあるか
- コメントが中身のない語だけで構成されていないか
- コメントがチケット番号に言及しているか
- 変更が承認された時間帯に行われているか
- フィールドの値が命名規則に合っているか
- 必須フィールドが実際に埋まっているか

さらに二つのモジュールが付属します。

- **パッチ管理** — 仮想マシンまたは物理サーバーごとのパッチ状況、OS、担当者、更新
  履歴。必要に応じて CheckMK から取り込みます。
- **Graylog** — 監査イベントを外部へ送り、ログ情報をその対象オブジェクトの隣へ
  持ち帰ります。

すべて任意です。導入直後はコメントの有無の確認だけが有効で、最小 2 文字です。他は
Web 画面で有効にします。

## 2. 前提条件

| 構成要素 | バージョン | 備考 |
|---|---|---|
| NetBox | 4.0.0 以上 | |
| Python | 3.10 以上 | |
| PostgreSQL | — | NetBox 自体が必要とします |
| `cryptography` | 任意 | NetBox に同梱。無い場合、CheckMK の秘密と Graylog のトークンは暗号化されずに保存され、プラグインは設定ページでそれを明示します |
| `requests` | 任意 | NetBox に同梱。CheckMK と Graylog に必要です |
| RQ プロセス | — | 定期的な CheckMK 同期と Graylog 取得のみに必要。無くても双方は手動で動作し、ページがその旨を示します |

## 3. インストール

### 3.1 パッケージの導入

```bash
source /opt/netbox/venv/bin/activate
pip install git+https://github.com/Gasi-Code/netbox-force.git
```

### 3.2 プラグインの登録

`configuration.py` に記述します。

```python
PLUGINS = ['netbox_force']
```

### 3.3 マイグレーションの実行

```bash
cd /opt/netbox/netbox
python manage.py migrate netbox_force
python manage.py collectstatic --no-input
```

### 3.4 NetBox の再起動

```bash
sudo systemctl restart netbox netbox-rq
```

### 3.5 Docker

```bash
docker exec -it <コンテナ> pip install git+https://github.com/Gasi-Code/netbox-force.git
docker exec -it <コンテナ> /opt/netbox/netbox/manage.py migrate netbox_force
docker restart <コンテナ>
```

LinuxServer.io のイメージでは、インストールに `custom-cont-init.d` スクリプトを
**使わないでください**。これらは NetBox 自身の初期化スクリプトの *後* に実行される
ため、マイグレーションが失敗することがあります。Docker Mods はその前に実行されます。

コンテナのファイルシステム内へのインストールはイメージ更新で失われます。イメージの
永続的なプラグイン導入の仕組みに追加してください。さもないと次の pull で消えます。

## 4. 更新

```bash
source /opt/netbox/venv/bin/activate
pip install --force-reinstall --no-cache-dir git+https://github.com/Gasi-Code/netbox-force.git
```

`--force-reinstall --no-cache-dir` が必要なのは、pip がバージョン番号でキャッシュ
するため、同じバージョンの再構築を省略してしまうからです。

**再起動する前に確認してください。** この手順は稼働中のプロセスに触れずにプラグイン
を読み込みます。エラーが出たら再起動しないでください。稼働中の NetBox はまだ旧
コードをメモリに保持しており、そのまま動き続けます。

```bash
cd /opt/netbox/netbox
python manage.py check
```

その後：

```bash
python manage.py migrate netbox_force
python manage.py collectstatic --no-input
sudo systemctl restart netbox netbox-rq
```

### 以前のバージョンへ戻す

```bash
pip install --force-reinstall --no-cache-dir \
  git+https://github.com/Gasi-Code/netbox-force.git@<commit>
sudo systemctl restart netbox netbox-rq
```

そのためにマイグレーションを戻す必要は通常ありません。追加された列は古いコードの
邪魔をしません。単に認識されないだけです。それでも更新前にデータベースの控えを
取ってください。

## 5. 設定ファイル

`PLUGINS_CONFIG` は **初期値のみ** を定めます。初回起動後は、すべての設定が Web 画面
で管理され、データベースに保持されます。

```python
PLUGINS_CONFIG = {
    'netbox_force': {
        'min_length': 2,
        'exempt_users': ['automation', 'monitoring', 'netbox'],
        'enforce_on_create': False,
        'enforce_on_delete': True,
        'extra_exempt_models': [],
        'checkmk_secret': '',
    },
}
```

| 設定 | 既定値 | 意味 |
|---|---|---|
| `min_length` | `2` | 変更ログの最小文字数 |
| `exempt_users` | 上記参照 | すべての確認を免除するユーザー名。大文字小文字は区別しません |
| `enforce_on_create` | `False` | 作成時にもコメントを要求する |
| `enforce_on_delete` | `True` | 削除時にもコメントを要求する |
| `extra_exempt_models` | `[]` | 追加の免除モデル、形式は `app.model` |
| `checkmk_secret` | `''` | 任意。CheckMK の秘密をデータベースの外に完全に置きます。設定した場合は画面の入力欄より優先されます |

## 6. 各ページ

スーパーユーザーはサイドバーに **NetBox Force** を見つけます。特記がない限り、すべて
のページはスーパーユーザー限定です。

| ページ | 目的 |
|---|---|
| **設定** | すべての強制規則、免除、モジュール、Webhook、CheckMK |
| **検証ルール** | 命名パターンと必須フィールド、モデルおよびフィールドごと |
| **モデルポリシー** | モデルごとの全体設定からの逸脱 |
| **違反** | 阻止された変更の絞り込み可能な記録。CSV で書き出し可能 |
| **Graylog** | 送信と読み取り。第 7 章および第 8 章を参照 |
| **ダッシュボード** | 統計：有効な機能、阻止された変更、上位ユーザー、30 日間の推移 |
| **インポートテンプレート** | NetBox の一括インポート用の CSV テンプレート。有効時はログイン済みの全ユーザーに表示 |
| **手引き** | 自組織のユーザー向けの自由記述ページ。有効時はログイン済みの全ユーザーに表示 |
| **パッチ管理** | 第 9 章を参照 |

特に触れておくべき設定が二つあります。

- **全体スイッチ** — 保守作業中などに、すべての確認を一時停止します。
- **試行モード（dry-run）** — 違反を記録しますが何も阻止しません。新しい規則を導入
  する正しい方法です。実際に誰かが止められる前に、何が阻止 *されていたか* が分かり
  ます。

## 7. Graylog — 送信

監査イベントを NetBox から Graylog へ GELF で送ります。

### 目的

NetBox の他のどこにも記録されないものが三つあります。

- **失敗したログイン。** NetBox はまったく保持しません。
- **変更の送信元 IP とユーザーエージェント。** NetBox の変更ログはいずれも持ち
  ません。
- **プラグイン自身の設定変更。** NetBox の変更ログの対象外であり、強制を無効にした
  人はこれまで何の痕跡も残しませんでした。

### 設定

**Graylog** ページの上半分：ホスト、ポート、トランスポート。続いて *テストイベントを
送信*。

まず **UDP** で始めてください。何も届かない場合は **TCP** に切り替えます。UDP は
仕組み上、失敗を報告できませんが、TCP はできます。これで「ポートが違う」のか「メッ
セージが破棄された」のかを切り分けられます。

| トランスポート | 到達を確認 | 暗号化 |
|---|---|---|
| UDP | いいえ | いいえ |
| TCP | はい | いいえ |
| TCP + TLS | はい | はい |
| HTTP | はい | いいえ |
| HTTPS | はい | はい |

UDP はローカルネットワーク内では正しく、インターネット越しでは誤りです。

### 送信される内容

イベント種別ごとに 1 行、それぞれチェックボックスと syslog の重大度を伴います：
オブジェクト作成・変更・削除、ログイン、ログアウト、ログイン失敗、阻止された変更、
プラグイン設定の変更。

### 量

設定したしきい値より多くのオブジェクトを変更したリクエストは、**1 件の要約イベント**
として報告されます。500 台の機器の取り込みは 1 つの操作であり、ほぼ同一の 500 行は
それを見えにくくするだけです。

絞るのではなく要約するのは意図的な選択です。埋まる速さより遅く空くキューは、*最も
新しい* イベントを捨てます。つまり残すべきでない側を残してしまいます。

### フィールド名

すべてのイベントが同じフィールドを持つため、検索は単純なままです。

```
_app          netbox_force
_category     object_change | auth | violation | settings
_event        object_created, login_failed, …
_username
_client_ip
_user_agent
_object_type  dcim.device
_object_id
_object_name
_action       create | update | delete
_changed_fields
_request_id
_netbox_url
_outside_business_hours
```

`_request_id` は 1 回のリクエストが変更したすべてをまとめます。40 台を一括編集した
のは 1 つの操作であり、40 個の謎ではありません。

### 知っておくべき三点

- **Graylog の停止が NetBox の保存を遅らせたり失敗させたりすることはありません。**
  イベントは上限のあるキューに入り、バックグラウンドのスレッドが送信します。キューが
  満杯になると新しいイベントは破棄されて数えられ、その数がページに表示されます。
- **メッセージ本文は常に英語です。** 画面の言語に関わらず変わりません。Graylog の
  アラート検索はこの文字列に依存しており、翻訳すると誰かが言語を変えた瞬間にすべての
  アラートが静かに壊れます。
- **クライアント IP は `X-Forwarded-For` があればそこから読み取ります。** このヘッダー
  はクライアントが送るもので、NetBox がリバースプロキシなしで到達可能な場合は偽装
  できます。

## 8. Graylog — 読み取り

Graylog の情報を NetBox に取り込み、2 つ目のタブを開かずにホストを判断できるように
します。

### 設定

**Graylog** ページの下半分：Web アドレスと API トークン、続いて *接続をテスト*。結果
には Graylog のバージョン、判別された検索 API の形式、最も多いソース、利用可能な
ストリームが示されます。*今すぐ取得* は取得を即時に実行します。

**トークンは読み取り専用ロールを持つ Graylog ユーザーで発行してください。** NetBox
から Graylog を変更できないことを保証するのは、このプラグインのコードではなくその
ロールです。

### ここでの「読み取り専用」の正確な意味

すべての呼び出しはデータを取得するか、Graylog に検索の実行を依頼します。旧来の検索
エンドポイントは単純な `GET` です。新しい Views 検索 API は違い、検索を登録する
`POST` と実行する `POST` を必要とします。これにより Graylog 内に短命な検索オブジェクト
が生成され、結果が返ります。保存されたデータは変更されません。`GET` のみが許容される
環境では、設定で検索形式を `legacy` に固定してください。

### ソースと NetBox オブジェクトの対応付け

厳密に、この順で、最初に一致したものが採用されます。

| | 規則 |
|---|---|
| 1 | **手動の対応付け** — 一度設定すれば常に優先 |
| 2 | **IP アドレス** — ソースをオブジェクトの全 IP と照合 |
| 3 | **ホスト名**、大文字小文字は区別しない |
| 4 | **設定したドメイン接尾辞を除いたホスト名** |

それ以外はすべて未対応のまま残り、そのように一覧されます。

**あいまい照合は意図的にありません。** `srv-web-01` と `srv-web-02` は 1 文字違いです
から、どんな類似度尺度も 96 % 一致と判定します。しかし別々のマシンです。番号付きの
命名規則、つまり名に値するあらゆる NetBox では、最も似た候補が体系的に誤った相手に
なります。ログは隣のサーバーの下に整理され、誰も気づきません。類似度は未対応ソースの
横に並ぶ候補を **並べ替える** ためだけに使われ、それ自体が対応付けを行うことは決して
ありません。

Graylog の前に集約 syslog 中継がある場合、すべてのメッセージが中継の アドレスを持ち、
規則 2 は有用な一致を得られません。その場合はソース欄がホスト名を持つ必要があり、
規則 3 と 4 がそのためにあります。

### 各ページ

- **ソース** — Graylog が報告するすべて。カウンター付きで、対応済み・未対応・無音・
  未検出・無視で絞り込めます。
- **無音** — NetBox で対応付けられているのに何も送らなくなったもの。停止、ログ設定の
  破損、あるいは残骸です。どちらのシステムも単独では気づけません。
- **Graylog で未検出** — 突き合わせのもう半分。
- **クラスター** — 緑／黄／赤のランプ付きノード、インデクサーの健全性、ジャーナルの
  滞留。各ノードは対応する NetBox の仮想マシンへリンクされます。
- **オブジェクト上** — 対応付けられたソースを持つ機器と仮想マシンには、カウンター、
  要求に応じた直近メッセージ、Graylog へのリンクを備えたパネルが表示されます。

### 負荷と安全性

- 1 回の取得は **全ホストをまとめた 1 つのクエリ** であり、機器ごとのクエリでは
  ありません。800 台の拠点でもリクエストは 3 回です。
- クラスターパネルとメッセージ一覧はページ描画の **後** に読み込まれます。Graylog が
  遅い、あるいは停止していても、空のパネルになるだけで NetBox のページが固まることは
  ありません。
- 対応付けはプラグイン自身のテーブルにあります。**Graylog が NetBox の中核オブジェクト
  に書き込むことはありません。** プラグインを削除すれば対応付けも消え、NetBox は
  損なわれません。
- メッセージのエンドポイントは、呼び出し元が閲覧を許可されているオブジェクトに対応
  付けられたソースについてのみ応答します。

## 9. パッチ管理と CheckMK

仮想マシンまたは物理サーバーごとに、パッチ状況、OS、担当者、更新履歴を管理します。

- **状態** 緑／黄／赤。手動で維持するか CheckMK から読み取ります。
- **遅延しきい値** — N 日以内にパッチが当たっていない項目は遅延として印が付きます。
- **エスカレーション** — N 日 *黄* のままの項目は自動的に *赤* になります。
- **連絡先** — NetBox の連絡先オブジェクトから管理者と業務責任者。
- **更新履歴** — パッチ適用ごとに 1 件、チケット番号と備考付き。
- **アクセス権** は Django の権限ではなく、プラグイン設定の NetBox グループ名で与え
  ます。

### CheckMK

連携は **pull** です。NetBox が CheckMK から読み取ります。CheckMK へは何も書き込まない
ため、読み取り専用の自動化ユーザーで足ります。

設定ページで構成します：サイト URL、自動化ユーザー、秘密、サービスフィルター、同期
間隔。秘密は暗号化して保存され、二度と表示されません。

止まった同期はもっとも厄介な障害です。ページは、静かに正しくなくなったパッチ状況を
表示し続けるからです。そのためダッシュボードは、直近の成功した同期が設定間隔の 2 倍
より古くなった時点ではっきりとそれを告げます。

## 10. トラブルシューティング

**プラグインがサイドバーに現れない。**
`configuration.py` に `PLUGINS` を設定しましたか。マイグレーションは実行しましたか。
NetBox を再起動しましたか。サイドバーのラベルは再起動時にのみ更新されます。プラグイン
内のタブは即座に更新されます。

**変更が阻止されない。**
この順で確認してください：全体スイッチ、試行モード、対象ユーザーが免除ユーザーまたは
免除グループに含まれていないか、そしてモデルポリシーがそのモデルの強制を無効にして
いないか。

**ページが列の欠落を報告する。**
マイグレーションが未実行、または一部のみ実行されています。
`python manage.py migrate netbox_force`。

**「バックグラウンドワーカーが動いていません」。**
`netbox-rq` が動いていません。CheckMK 同期と Graylog 取得はボタンを押したときのみ
実行されます。

**Graylog に何も届かない。**
トランスポートを UDP から TCP に切り替えてください。UDP は失敗を報告できませんが、
TCP は報告でき、そのエラーメッセージがポートの誤りか拒否かを示します。

**機器の Graylog パネルが空のまま。**
その機器にソースが対応付けられていません。*ソース → 未対応* から対応付けるか、FQDN を
短縮できるよう設定に自組織のドメイン接尾辞を追加してください。

**`SECRET_KEY` を変更したら CheckMK の秘密や Graylog のトークンが使えなくなった。**
どちらも `SECRET_KEY` から導かれた鍵で暗号化されています。入力し直す必要があります。

## 11. 言語の変更

言語はユーザーごとではなく **インストール単位** の設定です。設定ページで変更します。

プラグイン内のタブとページはただちに切り替わります。サイドバーのラベルは起動時に一度
だけ構築されるため、NetBox を再起動するまで変わりません。

阻止時にユーザーへ表示されるメッセージはこの設定に従います。API のエラーメッセージと
Graylog へ送るメッセージは英語のままです。[ドキュメント索引](../README.md)の注記を
参照してください。
